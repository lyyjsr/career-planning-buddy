## 1. 项目背景

### 1.1 用户问题

计算机学生在求职准备过程中，核心困难不是缺少信息，而是**信息过载、路径不清、计划过重、行动启动困难和焦虑反复**。

市面上的产品要么给海量内容让用户自己筛（题库、招聘平台），要么给空待办让用户自己填（任务管理工具），要么被动问答交给用户自己追问（通用大模型）。

**没有一个产品帮用户回答："我今天先做什么？"**

### 1.2 为什么是现在

- LLM + 联网搜索 + RAG + 受控工作流已经能支撑"诊断→证据→规划→校验"的稳定流程
- 多模型分层（DeepSeek V4 + 小模型）让单次成本可控制在 ¥0.2 内
- LangGraph 1.x 生产就绪，能做有状态的长任务工作流
- 同时市场上无人做"诊断→规划→今日小步"的前置链路（详见可行性分析报告）

### 1.3 竞品格局

| 赛道 | 代表 | 共性缺口 |
|---|---|---|
| 求职辅导 | 超级简历、BOSS、牛客 | 集中在简历/刷题/匹配末端，无人做前置规划 |
| 考公备考 | 粉笔、华图 | 重内容/题库，AI 只做批改 |
| 任务管理 | 番茄/滴答 | 只管"强制做"，不管"该做什么" |
| 通用大模型 | 豆包、Kimi、DeepSeek | 被动问答，无任务状态闭环 + 无统一记忆 + 无来源核查 |

## 2. 需求目标

### 2.1 业务目标

验证核心假设：**单核心 Agent + 受控工作流 + 证据驱动，能否把混乱信息收敛成用户今天愿意开始并完成的第一步，并形成"计划→执行→复盘→调整"的闭环。**

### 2.2 衡量指标

**北极星指标：每周第一步完成率（Weekly First-Step Completion Rate）**

定义：过去 7 天内完成 ≥1 个 starter_action 的用户 / 7 天内生成过计划的用户。

为什么是它：
- 比计划采纳率更深一层——采纳只是"点了开始"，第一步完成才是"真的做了"
- 同时验证三件事：① 用户信任 AI 计划 ② 计划真的可执行 ③ 低压力策略有效

| 类型 | 指标 | MVP 目标 |
|---|---|---|
| 🔥 北极星 | 每周第一步完成率 | ≥ 35% |
| 业务 | 计划采纳率 | ≥ 50% |
| 业务 | 复盘提交率 | ≥ 30% |
| 业务 | 7 日回访率 | ≥ 15%（无主动推送） |
| 质量 | 计划过重率 | ≤ 20% |
| 质量 | 来源可靠率 | ≥ 70%（命中场景内） |
| 技术 | Agent 成功率 | ≥ 95% |
| 技术 | 结构化输出通过率 | ≥ 98% |
| 技术 | 受控 Loop 触发率 | ≤ 30% |
| 技术 | 单次运行成本 | ≤ ¥0.2 |
| 技术 | 端到端延迟 | P95 ≤ 20s |

### 2.3 MVP 成功标准

4 项全部达标才算成功：

| 维度 | 标准 |
|---|---|
| 质量覆盖 | 1 首发场景跑通 30 case（含正常/异常/边界），通过率 ≥ 85% |
| 北极星 | 每周第一步完成率 ≥ 35%（上线后测） |
| 计划质量 | 计划过重率 ≤ 20% |
| 安全合规 | 心理危机误判/漏判 = 0 |

判定：
- 4 项全达标 = MVP 成功
- 3 项达标 = MVP 基本成功，剩余 1 项进入迭代
- ≤ 2 项 = MVP 未达预期，按 Plan B 调整

## 3. 目标用户与场景

### 3.1 核心用户

| 类型 | 典型状态 | 主要需求 |
|---|---|---|
| 方向模糊型 | 知道想做后端/Agent 但不了解能力差距 | 理解岗位要求，确定阶段路线 |
| 计划过重型 | 准备事项过多，每天列长清单 | 限制任务数量，降低启动成本 |
| 执行摇摆型 | 完成几天后中断，不知道怎么调整 | 根据实际行为重规划 |
| 临近秋招型 | 距离投递或面试时间短 | 按截止时间和优先级压缩路线 |
| 项目包装型 | 做过项目但不会整理 | 把项目完善拆成任务 |

### 3.2 MVP 首发场景（聚焦单一）

**MVP 只做 1 个场景：计算机学生 AI / 后端 / Agent 应用方向求职准备**

理由：
- 聚焦单一知识域，便于做深规划逻辑、知识库和评测
- 1 个场景做透比 3 个场景做溅更有秋招说服力
- 单一场景的 5 维质量评分更容易迭代到位

### 3.3 **通用化扩展性设计**（从第一天就要建好）

即使 MVP 只做 1 场景，数据模型和 Agent 设计不能写死。3 个设计原则：

| 设计原则 | MVP 实现 | 演进价值 |
|---|---|---|
| `goal_type` 字段化 | 建档必填，枚举 `ai_backend / agent_app / backend_java / data_engineer / fullstack / other` | 加 goal_type 不需要改模型 |
| 经验原子按 goal_type 索引 | `experience_atoms` 表带 `goal_type` 字段 + 向量索引 | 加场景 = 加数据 |
| Prompt 按 goal_type 分目录 | `prompts/{goal_type}/diagnose_v1.py`、`plan_v1.py`、`review_v1.py` | 加场景 = 加模板 |

**演进路径**：
```
阶段 A：1 场景做透（MVP）
  ↓ 抽象出 SceneConfig（goal_type + 经验原子 + Prompt 模板）
阶段 B：通用化准备
  ↓ 诊断 Agent 识别 goal_type，命中即用专属知识，未命中 fallback
阶段 C：加新场景
  ↓ 加经验原子 + 加 Prompt 模板，Agent 架构不变
阶段 D：真正通用
  ↓ 任意 goal_type：命中走专属；未命中走通用模板 + 坦诚告知
```

**参考做法**：Dify 的"应用模板"、LangChain 的 AgentExecutor + 多 Prompt、ChatGPT 的 Custom GPTs——配置/指令/知识库三层分离。

**未支持场景（goal_type=other）的产品行为**：
- 不拒绝用户、不限制入口
- 坦诚标注"⚠️ 通用建议，我们还没积累这个方向的经验库"
- 仍然给出基础规划（LLM 通用能力 + 联网搜索 + 用户记忆）
- 5 维质量评分照样跑

### 3.4 场景边界

| 场景 | 做 | 不做 |
|---|---|---|
| 求职路径规划 | 整体方向 + 本周重点 + 今日任务 | 不替代专业心理咨询/医疗/法律/金融 |
| 情绪记录与陪伴 | 复盘记录 + 6 时刻反馈话术 | 不做心理诊断/治疗 |
| 动态信息核查 | 招聘/JD 联网 + 来源标注 | 不保证 100% 准确，以官方为准 |

## 4. 产品方案

### 4.1 一句话定位

面向计算机学生的 AI 求职规划搭子：通过单核心 Agent + 证据驱动 + 统一记忆 + 计划校验，把分散信息转成用户今天可以开始的行动。

### 4.2 "陪伴"的产品行为定义

"陪伴" = **记忆驱动个性化**（功能层）+ **关键时刻反馈话术**（表达层）。

| 触发时刻 | 陪伴行为 |
|---|---|
| 用户首次完成任务 | 非泛泛庆祝，引用具体完成内容 |
| 用户放弃任务 | 非评判式（不说"怎么又放弃"），记录原因后温和调整 |
| 用户连续放弃 N 天 | 主动降到 1 个任务/天 + 共情话术 |
| 复盘情绪低落 | 共情但不 diagnose |
| 次日续上 | 引用昨日记忆，不冷冰冰重启 |
| 规划等待中 | 每 3-5s 更新"正在结合 X 月 X 日的复盘..." |

### 4.3 单核心 Agent + 受控节点

不包装成多 Agent。架构上只有 1 个真 Agent（CareerPlanningAgent），其余是工作流节点。详细见 TDD 第 4 章。

## 5. 用户旅程

### 5.1 Happy Path

```
首次进入
  ├─ 建档：goal_type/stage/available_minutes（必填）+ 可选字段
  │    └─ 缺必填 → risk_gate + intent_router 判断缺槽位 → clarification
  │
  ├─ 生成规划（Plan Run）
  │    ├─ risk_gate：安全分流
  │    ├─ intent_router：意图分类
  │    ├─ context_builder：拼画像 + 记忆 + 统计
  │    ├─ CareerPlanningAgent：自主调 web_search/rag_retrieve 生成候选
  │    ├─ rule_validator：5 维质量评分
  │    ├─ quality_reviewer：LLM Judge
  │    ├─ revise_or_fallback：重写 ≤2 或降级
  │    ├─ companion_response：生成陪伴反馈
  │    └─ persist：受控保存
  │
  ├─ 今日任务卡
  │    ├─ 开始 → in_progress
  │    ├─ 完成 → completed + 实际耗时
  │    └─ 放弃 → abandoned + reason
  │
  ├─ 每日复盘
  │    └─ 完成情况/情绪/阻碍/调整 → Service 保存 + 触发可选 replan
  │
  └─ 次日续上
       ├─ 读取昨日完成 + 复盘 + 记忆摘要
       └─ 规则驱动 + Agent 驱动双层调整
```

### 5.2 流失路径分析

| 流失时刻 | 用户内心 | 产品策略 |
|---|---|---|
| 建档（摩擦） | "又要填资料" | 3 必填，其余可后补 |
| 等待规划（15-20s） | "怎么这么慢" | 每 3-5s 进度提示 + 引用个性化记忆 |
| 看到任务卡（不信任） | "这不靠谱" | 来源标注 + "为什么这么建议" + "调整任务"按钮 |
| 做完第一天不回来（无激励） | "没感觉" | 首次完成庆祝 + 次日续接卡片 |
| 连续放弃（挫败） | "我不行" | 不评判 + 降到 1 个 + 共情 |
| 2 天未打开 | "忘了" | 回归话术 + 一键恢复 |

## 7. 5 维质量评分（核心质量约束）

每个候选任务必须通过 5 个维度的质量校验。**本节定义"什么是合格/不合格的产品判定标准"——具体校验执行机制（程序节点 vs LLM Judge、重写次数、降级路径）见 [TDD §8](../architecture/tdd.md)。**

| 维度 | 合格信号 | 不合格信号 |
|---|---|---|
| 可启动性 | starter_action 具体到"打开 XX / 新建 XX / 写下 XX" | "准备学习""了解概念" |
| 时段匹配 | 任务耗时 ≤ 用户当日可用时间 | 任务 4h 但用户今天 30min |
| 认知负荷 | 高产出动词（写、改、提交） | "理解 XX""熟悉 XX""研究 XX" |
| 连续性 | 与昨天完成 / 放弃 / 阻碍有关联 | 完全无视昨天上下文 |
| 完成可验证 | deliverable 可观测产物 | "提升认知""打好基础" |

**产品铁律**：宁可只给 1 个高质量任务，也不给 3 个低质量任务。

## 8. 复盘-调整双层规则（闭环核心）

每次复盘后，系统必须根据用户执行情况调整后续计划。**调整的产品意图和用户可见行为在本节定义；具体执行规则表（触发条件 → 确定性调整 → 话术模板）见 [TDD §9](../architecture/tdd.md)。**

### 8.1 双层调整的产品意图

| 层 | 设计意图 | 适用场景 |
|---|---|---|
| **规则驱动**（优先） | 用确定性规则覆盖高频模式，保证可解释、不漂移 | 连续放弃 / "本周很忙" / "方向动摇" / 连续完成 |
| **Agent 驱动**（兜底） | 规则不覆盖时由 LLM 综合判断，但必须明示理由 | 复盘内容复杂、规则外的偏好变化 |

### 8.2 调整红线（产品不可破的边界）

- **不擅自加量**——加量只在用户主动要求
- **不擅自改方向**——目标级变更必须用户确认
- **调整量上限**：单日任务量 ±2 个，耗时 ±50%
- **连续完成不奖励加量**——避免"完成 → 加压 → 放弃"陷阱
- **连续放弃触发降级而非催促**——共情优先于效率

- 远期上线完成企业注册 + 算法备案

### 9.4 成本
- 单 run ≤ ¥0.2
- 日活 1000 时日均 ≤ ¥200

## 10. 范围说明

### 10.1 MVP 做
- FastAPI 后端 + React 前端（本地 Web 端）
- 1 个垂直场景做透（AI/后端/Agent 求职）
- 1 个核心 Agent + 受控节点
- 5 个前端页面（今日/规划/任务/复盘/记忆）+ 开发者 Trace 页
- 30 case 固定评测集 + 自动 grader

### 10.2 MVP 不做
- Java 后端（演进触发才引入）
- 微信小程序（远期上线）
- 主动推送（MVP 用被动召回）
- 多 Agent / Swarm / 开放自治
- MCP 工具市场
- 变现/付费
- Redis / Celery / K8s（演进触发才引入）

### 10.3 重新评估时间点
- 上线后 1 个月：根据北极星决定是否加主动推送
- 上线后 2 个月：根据用户增长决定是否扩 goal_type
- 上线后 3 个月：根据成本决定是否做变现

## 11. 风险与 Plan B

### 11.1 主要风险

| 风险 | 应对 |
|---|---|
| 计划质量低 | 5 维评分 + 重写 ≤2 + 降级兜底 |
| 用户不信任 | 来源标注 + "为什么这么建议" + 免责 |
| 通用大模型向下覆盖 | 速度 + 经验原子沉淀 + 真单 Agent 工程深度 |
| LangGraph 调试难 | 接 LangSmith + Trace 完整 |
| 双 LLM Provider 失败 | 降级链 DeepSeek → GLM → 模板 |
| 合规 | 远期上线才做企业注册 + 备案 |

### 11.2 Plan B（假设失败）

| 指标不达标 | 应对 |
|---|---|
| 北极星 < 35% | 5 用户深度访谈 + "30 分钟启动原则" |
| 计划过重率 > 20% | 单任务 ≤60min 硬上限 |
| 复盘提交率 < 20% | 改为 1 问 1 答 |
| 7 日回访率 < 10% | 加"成长轨迹"页 + 订阅消息 |
| 通用场景质量明显低 | 退回"诚实告知"+ 扩经验库 |
| Agent 通过率 < 85% | 升级到更强模型 |
| 单 run 成本 > ¥0.2 | 限频次 + 优化 Prompt |
| P95 > 20s | 两段返回（先方向后任务） |

## 12. 开发节奏（阶段化交付，不绑时间）

详见 [../governance/stage-delivery-definition.md](./../governance/stage-delivery-definition.md)。摘要：

| 阶段 | 退出条件 |
|---|---|
| 0 工程基线 | 骨架启动 + 架构测试绿 + docs 就位 |
| 1 契约冻结 | PRD/TDD/API 评审通过 + OpenAPI + Pydantic + DB 迁移 + 契约测试 |
| 2 纵切骨架（Mock） | 端到端 1 次 plan_run 跑通（Mock） |
| 3 真实模型注入 | DeepSeek 接入 + 1 场景跑通 + Trace 完整 |
| 4 证据增强 | Web Search + RAG + 来源入库 + 30-50 经验原子 |
